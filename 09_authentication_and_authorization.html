Chapter the Ninth

Authentication, Authorization & Identity Protocol

"Authentication is the administrative ledger that answers the question: Who are you? Authorization is the sovereign permit that dictates: What are you allowed to do?"
♦ ✦ ♦

In the grand bureaucracy of a digital city, every user transaction is subject to the strict laws of identification. To govern this space, we rely on two separate administrative treaties.

Authentication answers a single question: Who are you? When a traveler arrives at a national border, they present a passport containing their photograph and national seal. The border guard inspects the passport, validates the seal, and confirms their identity.

Authorization answers a secondary, highly different question: What are you allowed to do? Once the traveler is inside the city, their passport does not grant them entry into secure bank vaults or military headquarters. They must present a security clearance permit. If their role is "Visitor," they are blocked; if their role is "Governor," the heavy steel gates open automatically.

In modern web applications, we must implement both gates. We started with stateful memory tables, but as scale demanded, we evolved to stateless cryptographic seals (JWTs) and third-party delegation frameworks.

1. The Great Memory Crisis: Stateful Sessions

HTTP is fundamentally a stateless protocol. It treats every incoming request as a brand new transaction with zero memory of the past. To enable dynamic behaviors like shopping carts, engineers forged Stateful Sessions.

When a user logs in, the server allocates a small block of memory in its RAM, maps a unique identifier to it (e.g., session_id = "9283"), and sends it back in a Set-Cookie header. The browser automatically attaches this cookie on every subsequent call. The server reads the ID, looks it up in RAM, restores the user state, and processes the request.

However, sessions introduced the Scalability Bottleneck. If you run 10 servers behind a load balancer, Server A does not share the memory heap of Server B. If a user logs in on Server A, and their next request lands on Server B, Server B will reject it as unauthorized! This forced developers to build centralized Redis session databases or use sticky sessions, creating massive latency, high cost, and single points of failure.

2. The Stateless Covenant: JSON Web Tokens (JWT)

To escape the stateful prison, engineers designed JWTs. Instead of storing user state in the server's memory, the server serializes the user state, signs it, and hands it to the client to hold. The client becomes the archivist of their own identity.

A JWT is a flat ASCII string divided into three distinct zones separated by dots:

  • Header: A JSON block containing token metadata, like the hashing algorithm used (e.g., HS256), encoded in Base64URL.
  • Payload: The data claims. It contains the user's ID (sub), their name, their roles (isAdmin), and the token's expiration timestamp (exp). Anyone can decode this Base64 payload, so you must **never** store sensitive secrets inside it!
  • Signature: The cryptographic seal. It is computed by taking the Header and Payload and hashing them together with a secret key known only to the server: HMACSHA256(Base64(Header) + "." + Base64(Payload), secretKey).

When a request carrying a JWT arrives, the server slices the token, computes a signature using its secret, and compares it with the incoming seal. If they match, it immediately trusts the payload claims. Zero database queries. Infinite scalability.

3. The Disadvantages and the Hybrid Protocol

However, JWTs introduce a major security flaw: The Revocation Nightmare. Because the server does not track issued tokens, you cannot revoke a token once it is issued. If a user’s token is stolen, the attacker can query your database until the token expires, and you are powerless to stop them.

To solve this, modern backends implement a Hybrid Token Protocol:

  • Access Token: A stateless, short-lived JWT (expires in 15 minutes) sent in memory to authorize fast, high-volume API queries.
  • Refresh Token: A stateful, long-lived token stored in a database (like Redis) and sent inside a secure cookie (expires in 7 days).

When the access token expires, the client sends the refresh token to `/refresh`. The server checks the Redis database; if the refresh token is valid and has not been revoked, it issues a new 15-minute access token. If an account is compromised, the admin deletes the refresh token from Redis, ending the session in 15 minutes. This achieves 99% stateless scale with 100% revocation control.

4. The Fortress of Cookies: Secure Cookie Settings

If you store tokens in localStorage, your tokens can be stolen by malicious JavaScript in **XSS (Cross-Site Scripting)** attacks. To protect them, we must store tokens inside **Secure HTTP-Only Cookies** using three attributes:

  1. HttpOnly: Completely blocks JavaScript from accessing the cookie. Even if XSS occurs, scripts cannot read `document.cookie` to steal your token.
  2. Secure: The browser will only transmit the cookie over encrypted HTTPS connections, preventing network eavesdropping.
  3. SameSite=Lax/Strict: Blocks **CSRF (Cross-Site Request Forgery)** attacks by preventing the cookie from being sent on cross-site form submissions.

5. OAuth 2.0 Delegation & OpenID Connect

When a third-party application (like a print shop) wants to access your Google Photos, you should never type your raw Google password into their website. This challenge led to the development of OAuth 2.0—a delegation protocol.

OAuth 2.0 allows Google to issue a temporary, restricted **Access Token** to the print shop, granting it permission *only* to read photos for two hours, keeping your master password completely hidden.

Plate XX: OAuth 2.0 Delegation Flow

While OAuth 2.0 was designed for **Authorization** (access), OpenID Connect (OIDC) was built as an identity layer on top of it. OIDC introduces the id_token (strictly a signed JWT). When logging in via Google, the application receives an `access_token` to make photo queries, and an `id_token` containing the user's name and avatar to verify their identity.
