Serialization & Deserialization

"A study of the translation bridge between language-dependent in-memory graphs and flat, language-agnostic network streams, exploring XML, JSON, Protobuf, and prototype pollution security."
♦ ✦ ♦

In the month of July, 1799, near the port city of Rashid (Rosetta) in Egypt, French soldiers under the command of Pierre-François Bouchard discovered a large, dark slab of granodiorite stone. The stone, dating back to 196 BC, was inscribed with three identical versions of a royal decree issued by King Ptolemy V.

The three scripts were completely different in their cognitive, semantic, and structural systems: the top script was Ancient Egyptian Hieroglyphs—the ideographic, metaphorical language of the gods; the middle script was Demotic Script—a cursive, simplified daily script used for trade and administration; and the bottom script was Ancient Greek—a highly structured, phonetic, alphabetic system used for diplomacy and philosophy.

The scribes who carved the Rosetta Stone did not try to build a direct, fluid translator for every single word. Instead, they used the Greek text as a flat, standardized reference schema. Because they knew Greek was universally understood by the ruling classes across the Mediterranean, they could use it as a common standard. By translating their native, highly complex ideographic concepts into Greek, they preserved their meaning across thousands of years, allowing 19th-century scholars like Jean-François Champollion to decode the entire forgotten universe of ancient Egypt.

This is the Rosetta Stone Problem of distributed systems. Consider a common real-world backend scenario: your frontend is written in JavaScript, running inside Google's V8 engine in the browser; your backend is written in Rust, compiled to bare-metal machine code running on a server in Virginia. These two languages live in completely different universes of type representation and memory layout.

In JavaScript, a user object lives inside a garbage-collected, highly dynamic heap. It carries a prototype chain, supports dynamic runtime attribute modification, and represents every number as a 64-bit IEEE 754 floating-point value. In Rust, a user struct is a stack-allocated block of memory with strict compile-time ownership, zero runtime prototypes, statically defined fields, and distinct, sized integer types like u32, i64, and f64.

If JavaScript tried to hand its raw memory pointer directly to Rust, the result would be a catastrophic disaster. Rust has no concept of a V8 prototype. If Rust tried to parse JavaScript's raw memory address, it would read it as unaligned garbage, violate memory safety, and trigger a segmentation fault, crashing the server.

To bridge this language barrier, we do not write custom converters for every possible language pair. Instead, we agree on a common reference standard—a flat, language-agnostic serial string. We call the process of converting a dynamic, language-specific in-memory structure into this flat, transmittable format Serialization. We call the reverse process—reconstructing a private, language-specific memory structure from the flat format—Deserialization.

1. The Epistemology of the Memory Bridge

To appreciate the engineering challenge of serialization, we must understand the fundamental difference between In-Memory Objects and Network Streams. Inside the V8 Engine RAM, a JavaScript object is a complex, multi-dimensional, non-linear graph. It does not exist in a contiguous block. Instead, it consists of multiple nested properties, reference pointers to other addresses in the heap, prototype chain linkages, and metadata structures used by the garbage collector to trace active memory references.

If you tried to copy the raw raw binary memory block of a JavaScript object and send it over a TCP socket to a Python backend, the Python engine would look at the bytes with absolute confusion. The memory addresses are completely different in Python's heap, the garbage collection flags do not match, and Python has no concept of V8's hidden object shapes.

Plate XV: The Symmetrical Serialization Bridge

Let us trace what physically occurs inside the CPU when you invoke JSON.stringify(user). The JavaScript engine runs a Recursive Object-Graph Traversal Algorithm. It starts at the root node `user`. It walks its properties sequentially. It reads key `id`, matches its type (Number), and translates the value to a string of text bytes representing `42`. It encounters nested properties, recursively calling the stringify loop for child nodes, compiling an abstract syntax stream.

Crucially, this traversal must handle circular references. If Object A references Object B, and Object B references Object A, a naive recursive loop will get stuck in an infinite spiral, allocating frames on the call stack until it crashes with a RangeError: Maximum call stack size exceeded error. To prevent this, `JSON.stringify()` strictly checks for circular chains and throws an error, forcing developers to flatten their data structures before serialization.

2. Chronological Tapestry: From ASCII Cards to Binary Varints

The history of data formats is a continuous journey to balance two competing desires: human-readability and machine efficiency.

Era I: Fixed-Width ASCII Punch Cards

In early mainframes, data was serialized to fit physical paper punch cards. These formats were strictly fixed-width grids. A layout treaty declared: "Columns 1 through 10 represent the User ID, columns 11 through 30 represent the Username, and columns 31 through 38 represent the Date."

If your username was only five letters, you had to pad the remaining 15 spaces with blank characters. If your username was 21 letters, it overflowed its boundary, corrupting the Date column. While incredibly fast to parse (the CPU simply sliced arrays at hardcoded index markers), these formats were extremely brittle: changing a column size required rewriting every single database script in your system.

Era II: XML (1996) — The Bloated Giant

By 1996, the industry demanded a highly flexible, extensible format. The W3C formalized XML (eXtensible Markup Language). XML was a massive upgrade: it allowed infinite nesting, supported robust metadata schemas (XSD) that could validate types at compile-time, and supported complex Namespaces to prevent field collisions.

However, XML was violently bloated. Consider this XML representation of our liked post request: 

<?xml version="1.0" encoding="UTF-8" ?>
<request>
  <user_id>harshit_87</user_id>
  <action>like</action>
</request>

To transmit exactly 14 bytes of actual cargo data (`harshit_87` and `like`), XML consumes 107 bytes of tag metadata! Under high traffic, web servers spent more CPU cycles and bandwidth parsing and transmitting tag syntax characters than actual payload data.

Era III: JSON (2001) — The Minimalist Revolution

In 2001, Douglas Crockford extracted a tiny subset of the JavaScript programming language standard and presented it as JSON (JavaScript Object Notation), formalized in RFC 4627. JSON was a minimalist masterpiece: it did away with complex XML tags, namespaces, and schemas.

It relied entirely on four basic key-value data structures: strings, numbers, booleans, and null, wrapped in brackets `[]` and curly braces `{}`. Our post request in JSON consumes only 42 bytes, slashing transoceanic fiber transit overhead by 60% compared to XML.

Because JavaScript engines could parse JSON natively with high-speed C++ engine calls, JSON quickly defeated XML, becoming the undisputed king of web APIs.

Yet, JSON is not without its limitations: JSON is strictly a text format. If you want to transmit an image or a PDF inside a JSON payload, you must encode the file into a Base64 text string, which inflates the file size by exactly 33%, wasting massive bandwidth. Additionally, JSON represents numbers using JavaScript's native IEEE 754 double-precision floating-point format. If you try to transmit massive 64-bit integers (common in database IDs), the browser will lose precision during parsing, corrupting the numbers.

Era IV: Binary Protocols (Protobuf) — The Speed of Light

For high-performance microservices (such as gRPC inside your private backend VPC network), even JSON is too slow. Google designed Protocol Buffers (Protobuf) as a compact binary alternative. In Protobuf, we discard human-readability entirely.

First, both client and server must share a pre-compiled structural schema file: 

message LikeRequest {
      string user_id = 1;
      string action = 2;
}

Because both sides share this blueprint, the server *knows* that the first field is a string tracking `user_id` and the second is a string tracking `action`. During serialization, Protobuf completely strips away all field names. It does not transmit the characters `"user_id"` or `"action"` at all. Instead, it encodes the data into a compact binary packet where each field is represented by a small Field Tag and a type length marker.

Furthermore, Protobuf packs integers using Varints (Variable-Length Quantized Integers). Varints use the Most Significant Bit (MSB) of each byte as a continuation flag. If the MSB is set to $1$, it means more bytes of the number follow; if it is set to $0$, it is the last byte of the number. Through this math, the number `3` is packed into exactly one single byte instead of four, saving vast network bandwidth.

3. The Trojan Horse: The Security Vulnerabilities of Deserialization

While serialization seems like a passive data operation, Deserialization is one of the most high-risk security attack surfaces in computing. Why? Because when a server deserializes a client's request, it is reconstructing an object graph and executing logic inside its own runtime space *based on instructions provided by the untrusted client*.

Let us trace two devastating vulnerabilities that illustrate this threat: Python Pickle Exploitation and Node.js Prototype Pollution.

Python Pickle Exploitation

Python’s built-in serialization library is called Pickle. Pickle is incredibly powerful: it can serialize not just data rows, but entire Python classes, logic structures, and functions. If a developer naively deserializes a pickle file sent by a user: data = pickle.loads(req.body)

An attacker can craft a malicious pickle payload smuggling a custom class with a magic __reduce__ method. In Python, the `__reduce__` method dictates how an object should reconstruct itself during unpickling. The attacker overrides this method to return a system call: return (os.system, ('rm -rf /',))

The moment your server executes `pickle.loads()`, the engine runs the `__reduce__` instruction. Instantly, the server executes the destructive terminal command inside its own OS context, allowing the attacker to wipe the server, download malware, or spawn a reverse shell.

Node.js Prototype Pollution

In JavaScript, objects inherit base methods and properties from their prototype (typically `Object.prototype`). If an application uses a naive recursive deep-merge utility to merge user inputs into a database object: 

function deepMerge(target, source) {
  for (let key in source) {
    if (typeof target[key] === 'object') {
      deepMerge(target[key], source[key]);
    } else {
      target[key] = source[key];
    }
  }
}

An attacker can submit a malicious JSON payload carrying the magic key __proto__: 

{
  "__proto__": {
    "isAdmin": true
  }
}

When the server runs `deepMerge()`, it reads the key `__proto__`. Because `__proto__` is a special property that references the base prototype, the merge function traverses down, matching `Object.prototype.isAdmin = true`.

The attacker has successfully polluted the base prototype of the entire Node.js runtime. From this millisecond on, *every single object* created inside your Node server—even an empty object `{}`—will inherit the property `isAdmin: true`!

If a subsequent request evaluates a user’s permissions using a standard check: if (user.isAdmin) { grantAccess(); }

The check evaluates to true for every single visitor in the system, granting administrative control to anonymous users.

To prevent these attacks, backends must construct a Safe Parsing Shield:

  • Avoid Insecure Libraries: Never use Python Pickle or Java `ObjectInputStream` to parse untrusted client data. Use strict, static formats like JSON.
  • Prototype Protection: If merging JSON objects in Node, explicitly block keys matching `__proto__` or `constructor` to prevent recursive prototype pollution.
  • Payload Size Limits: Set strict limits on the raw body size allowed in incoming requests (e.g., maximum 100KB for API JSON payloads) to protect your parser against CPU-exhaustion Denial of Service (DoS) attacks.
