Chapter the Seventh

Serialization & The Language Barrier

"On the translation bridge between language-dependent in-memory graphs and flat network streams, the archeological history of structured data, and the cryptographic perils of unpickling untrusted payloads."
♦ ✦ ♦

In the sweltering monsoon of 250 BC, in the royal chambers of Pataliputra, a team of high-court scribes gathered before Emperor Ashoka the Great.¹ The Emperor had formulated a monumental, highly sophisticated ethical decree—his master philosophy of Dhamma. It was a multi-dimensional, complex system of governance, spiritual duty, and administrative order meant to unite a massive, ethnically diverse empire stretching from the Himalayas to the Deccan.

The imperial court faced a massive translation problem. Ashoka's unified, in-memory royal decree was a complex, deeply nested web of philosophical intents. It contained relationships between religious tolerance, family respect, wildlife conservation, and administrative transparency. Yet, to broadcast this intent across thousands of miles of rugged terrain, the scribes had to do something radical: they had to flatten it.

They took the rich, multi-dimensional logical graph of Ashoka’s intent and carved it into the flat, two-dimensional surfaces of massive rock pillars. But they could not use a single language. In the northern provinces, the decree was flattened into Brahmi Script, the phonetic alphabet of the Indo-Aryan heartland. In the rugged mountain passes of the northwest, it was carved in the cursive, right-to-left lines of Kharosthi Script. In the western trade outposts of Kandahar, the same royal decree was translated and flattened into Greek and Aramaic stone surfaces to accommodate Mediterranean merchants.

When a local governor or citizen stood before a rock pillar in Kandahar or Taxila, they did not read Ashoka's mind directly. They looked at the flat, 2D characters carved on the stone, ran them through their regional language schemas, and reconstructed Ashoka's original multi-dimensional ethical code inside their own minds.

If the scribes had made a mistake during the flattening process—if they had scrambled the script parameters or skipped a structural character—the regional governor would have parsed unaligned garbage. He might have interpreted a decree of non-violence as a declaration of war, leading to a catastrophic administrative failure.

We are dealing with the exact same Ashokan Rosetta Stone problem inside every computer network on Earth.

Consider a standard real-world backend scenario: your frontend application is written in JavaScript, running inside Google's V8 engine in a browser in London. Your backend application is written in Rust, compiled to machine code, running on a Linux kernel in a data center in Virginia. These two programs live in entirely separate mental universes.

In JavaScript, a user object lives inside a garbage-collected, highly dynamic heap. It has no fixed size. It carries a prototype chain that allows it to inherit properties dynamically at runtime. It represents every number, whether an integer or a decimal, as a 64-bit IEEE 754 floating-point value. In Rust, a user struct is a statically defined, contiguous block of stack or heap memory. It has compile-time ownership bounds, zero runtime prototype chains, and uses distinct, precisely sized integer types like u32 or i64.

If your JavaScript frontend tried to copy the raw memory pointer of its user object and send the bytes directly over a TCP socket to the Rust backend, the result would be a catastrophic crash. Rust has no concept of a V8 hidden class shape. If the Rust program tried to read that raw memory block, it would interpret the V8 garbage collection flags and pointer tables as unaligned garbage, violate memory safety, and trigger a segmentation fault, crashing the server immediately.

To cross this language barrier, we do not write custom converters for every possible pair of languages. If we did, we would need \(N(N-1)/2\) converters, meaning a system with ten different languages would require forty-five unique translation engines. Instead, we agree on a common standard—a flat, language-agnostic stream of characters or bytes.

We call the process of converting a language-specific, multi-dimensional in-memory structure into this flat, transmittable stream Serialization. We call the reverse process—reconstructing a private, language-specific memory structure from the flat stream—Deserialization.

I. The Memory Abyss: RAM Heap vs. Network Stream

To appreciate the engineering challenge of serialization, we must look at the difference between how an object lives in your program’s memory and how it travels over a network wire.

Inside the RAM of a running process, an object is not a flat string of characters. It is a complex, non-linear directed graph. It consists of multiple properties, reference pointers to other memory addresses in the heap, and metadata headers used by the garbage collector.

If you have a user object that has a reference to a profile object, which in turn has an array of references to post objects, these elements do not exist in a contiguous line. They are scattered across your RAM at arbitrary physical addresses. The "object" is merely a mental model constructed by the runtime engine, which traces these memory addresses at lightning speed whenever you write user.profile.posts[0].

Plate XV: The Symmetrical Serialization Bridge

But a network card is a physical device that transmits electrical or optical signals in a single, contiguous stream along a copper wire or glass fiber. It has no concept of "pointers." You cannot send a memory address over a fiber optic cable because the memory address the hidden marker refers to a specific physical transistor in your server in Virginia, not to any transistor in the laptop in London.

So we must flatten the graph.

Let us trace what physically happens when you run JSON.stringify(user) in JavaScript.

The engine does not perform a simple copy of your object’s memory block. It executes a recursive graph-traversal algorithm. It starts at the root node. It reads the first key, matches its type (for instance, a string), and translates the logical characters of that string into a sequence of UTF-8 bytes. It then walks down to the next key. If it encounters a nested object, it pauses, saves its position on the execution stack, descends into the child object, and runs the serialization loop on the child before returning to the parent.

The Cycle Trap

What happens if your object graph contains a circular reference?

Suppose Object A has a property friend that points to Object B, and Object B has a property friend that points back to Object A. This is a very common relational structure. If you pass this structure to a naive recursive stringifier, the algorithm will get trapped in an infinite loop. It will serialize Object A, which requires serializing Object B, which requires serializing Object A, and so on, until the execution call stack overflows its limits, and the engine crashes with a RangeError: Maximum call stack size exceeded error.

To prevent this, standard parsers like JavaScript's native JSON.stringify perform active cycle detection. They keep a temporary set of visited memory addresses. If they detect that they have encountered the same object reference twice during the active traversal path, they halt immediately and throw a TypeError: Converting circular structure to JSON exception, forcing you to manually flatten your relational schemas before sending them over the network.

II. The History of Data Interchange Standards

The history of data formats is a continuous struggle between human-readability and machine efficiency. We have oscillated between these two poles for fifty years, with each generation declaring the previous generation’s solution to be either too cryptic for humans to debug or too bloated for machines to parse.

Era I: Fixed-Width ASCII Punch Cards

In the early mainframes of the 1960s and 1970s, data was serialized to fit physical paper punch cards. These formats were strictly fixed-width grids. A data treaty declared: "Columns 1 through 10 represent the User ID, columns 11 through 30 represent the Username, and columns 31 through 38 represent the Date of Birth."

If your username was John, you had to pad the remaining sixteen characters with blank spaces. If your username was AlexandertheGreat, it would overflow the boundaries, and the last letters would bleed into the Date of Birth field, corrupting the database.

This was incredibly fast to parse. The CPU did not have to scan for delimiters or match tags; it simply sliced the array of bytes at hardcoded index offsets. But it was incredibly brittle. If you decided that you needed thirty characters for the username instead of twenty, you had to rewrite every single line of code in every program in your company, and run migration scripts to physically rewrite every punch card in your archives.

Era II: XML — The Bloated Giant

By 1996, the World Wide Web Consortium (W3C) formalized XML (eXtensible Markup Language) to solve this brittleness. XML was designed to be self-describing, extensible, and completely decoupled from physical grids. It supported infinite nesting, namespaces to prevent key collisions, and complex schema definitions (XSD) that could validate data types before processing.

Because JavaScript engines could parse JSON natively with high-speed C++ engine calls, JSON quickly defeated XML, becoming the undisputed king of web APIs.

Yet, JSON has its own structural limitations. It is strictly a text format. If you want to transmit a binary image or a PDF inside a JSON payload, you cannot embed the raw bytes directly because control characters would break the string boundaries. You have to encode the binary file into a Base64 text string, which inflates the file size by exactly 33%, wasting bandwidth.

Additionally, JSON represents numbers using JavaScript's native IEEE 754 double-precision floating-point format. If you try to transmit massive 64-bit integers (which are common for primary keys in databases like PostgreSQL), the browser will lose precision during parsing, silently corrupting your data.

III. JSON Under the Microscope: The Hidden CPU Parser Overhead

Many developers treat JSON.parse() as a free, instantaneous operation. In reality, text-based serialization imposes a massive tax on your server’s CPU. Let us trace what happens when your backend receives a 10MB JSON payload and begins parsing it.

1. Character-by-Character Tokenization

A text stream is just a flat sequence of characters. To reconstruct an object, the parser must run a Lexer that scans the string character by character. The lexer operates as a state machine. It must search for quotation marks (to identify keys), colons (to separate keys and values), curly braces (to manage object hierarchies), commas, and square brackets.

For every character, the CPU must fetch the byte from memory, execute a comparison, and jump to the correct branch of the state machine. Under high volume, this constant branching triggers severe CPU branch mispredictions, stalling the execution pipeline and forcing the processor to continually discard speculatively executed instructions.

2. The String Allocation Storm

When the parser identifies a key like "username", it cannot leave it as a reference in the flat network string. It must allocate a brand-new, independent string object in the heap.

If your JSON payload contains an array of one thousand users, the parser must execute thousands of heap allocations, generating high memory fragmentation and triggering aggressive GC pauses. The CPU spends more time running garbage collection sweeps than processing your business logic.

3. The Math of Float Parsing

Perhaps the most hidden performance tax in JSON parsing is Number Parsing. Inside a JSON string, a number is represented as ASCII text characters (e.g., "3.1415926535"). The database, however, needs to store this as a double-precision float in registers.

Converting a sequence of decimal characters into an exact, binary representation of an IEEE 754 floating-point number is an incredibly complex mathematical problem. The parser cannot just multiply digits by powers of ten. It must execute algorithms like Grisu3 or Ryū, running complex loops and high-precision division instructions in the floating-point unit (FPU), consuming massive CPU clock cycles compared to simply loading a pre-aligned binary number from a stream.

Varints and Zig-Zag Encoding

To pack integers, Protobuf uses Varints (Variable-Length Quantized Integers). In standard systems, a 32-bit integer always consumes four bytes of memory, even if the value is just 3 (the hidden marker).

Varints use the Most Significant Bit (MSB)of each byte as a continuation flag. The lower 7 bits of the byte contain the actual numerical data. If the MSB is set to \(1\), it means the number is large and more bytes follow. If the MSB is set to \(0\), this is the final byte of the number.

Using this math, the number 3 is encoded in exactly one single byte(the hidden marker) instead of four, saving vast amounts of network bandwidth.

However, standard Varints have a fatal flaw: negative numbers. Because negative numbers have their high-order bit set to \(1\) in two's complement notation, a negative integer like -1 would always consume the maximum ten bytes in a Varint encoding.

To solve this, Protobuf uses Zig-Zag Encoding. It maps signed integers to unsigned integers by zig-zagging back and forth across zero:

Through this simple bitwise operation, small negative numbers are converted into small positive numbers, allowing Varint encoding to compress them into a single byte as well.

2. MessagePack

If you want the byte efficiency of binary formats but do not want to manage static schema compilation files, you can use MessagePack.

MessagePack is a schema-less binary format. It is conceptually identical to JSON, but it replaces JSON’s text delimiters (colons, quotes, brackets) with small binary Type Markers.

For instance, instead of writing "username" (which consumes ten bytes in JSON including the quotes), MessagePack prefixes the raw characters with a single byte the hidden marker, which tells the parser: "The following 8 bytes are a raw string." MessagePack preserves the dynamic nature of JSON while slashing payload size by 30% to 50% and bypassing the need for lexical scanning.

3. Apache Avro

In big data pipelines (like Apache Kafka), data is streamed continuously by millions of producers. If you use Protobuf, you must distribute the compiled classes to every team. If you use JSON, your disk space costs will skyrocket.

Apache Avro solves this by using Schema-Attached Serialization. Avro files contain the entire JSON schema in the file header, followed immediately by the raw, highly compressed binary data records. Because the schema is built into the file itself, any system can read the file without pre-compiled classes, making it the gold standard for long-term database archiving and real-time event streaming.

VIII. Endianness and the Hardware Substrate: Memory Layouts and Network Stack Architecture

Beneath the neat abstractions of JSON strings, dynamic JavaScript heaps, and structured Rust structs, serialization must ultimately confront the raw, physical reality of computer hardware. Within a computer's random-access memory (RAM), the fundamental addressable unit is a single byte, consisting of eight bits. However, modern computing architectures constantly operate on multi-byte primitives—32-bit integers, 64-bit floating-point values, and 128-bit cryptographic hashes. These larger structures must span multiple consecutive byte addresses in hardware memory. The spatial arrangement of these bytes is not uniform across all microprocessors, leading to a fundamental architectural schism known as Endianness.

The terms Big-Endian and Little-Endian represent the two opposing methods of storing multi-byte data types in physical memory addresses. In a Big-Endian system, the most significant byte (the byte containing the most significant bits, or the "leftmost" byte in standard human notation) is stored at the lowest (first) memory address, while the least significant byte is stored at the highest memory address. Conversely, in a Little-Endian system, the least significant byte is stored at the lowest memory address, and the most significant byte is stored at the highest memory address.

To illustrate this physical distinction, consider a 32-bit unsigned integer representing the hexadecimal value \(0\text{x}12345678\). This value is composed of four distinct bytes: \(0\text{x}12\), \(0\text{x}34\), \(0\text{x}56\), and \(0\text{x}78\). Here, \(0\text{x}12\) is the most significant byte (MSB), and \(0\text{x}78\) is the least significant byte (LSB). If this integer is allocated at base memory address \(a\), the two architectures arrange the bytes in physical RAM as follows:

Physical Address Big-Endian Byte Layout Little-Endian Byte Layout
\(a\) (Base Address) \(0\text{x}12\) (MSB) \(0\text{x}78\) (LSB)
\(a + 1\) \(0\text{x}34\) \(0\text{x}56\)
\(a + 2\) \(0\text{x}56\) \(0\text{x}34\)
\(a + 3\) \(0\text{x}78\) (LSB) \(0\text{x}12\) (MSB)

This hardware-level layout choice is not arbitrary; it represents a deep division in processor design philosophy. Little-endian architectures, such as Intel x86_64, AMD64, and Apple/ARM64, are optimized for register operations. In a little-endian scheme, a low-level mathematical operation, such as type casting or arithmetic truncation, is trivial for the execution unit. If a 64-bit integer at address \(a\) needs to be truncated to a 32-bit integer, the execution unit can simply reuse the base address pointer \(a\) without modification. It reads the first four bytes and ignores the remaining four. In a big-endian processor, by contrast, the execution unit must calculate a mathematical offset addition (\(a + 4\) bytes) to locate the least significant portion, introducing a sub-register memory offset translation step in the ALU execution path.

Conversely, big-endian architectures match the intuitive left-to-right representation of numbers in human writing. In network protocol design, this alignment is highly beneficial. When serializing data to flow across a network socket, the bytes are transmitted one by one over the wire. If the most significant byte arrives first, routers and network interface cards (NICs) can inspect header fields (like IP addresses, port numbers, or packet flags) immediately as the stream begins to arrive, without needing to wait for the entire multi-byte word to be buffered. This allows for low-latency, on-the-fly routing decisions.

For this reason, the Internet Engineering Task Force (IETF) and early internet pioneers standardized on Network Byte Order, which is defined as strictly Big-Endian. This creates a permanent translation obligation for modern client and server hardware: since almost all consumer and server CPU architectures use Little-Endian natively as their Host Byte Order, every network packet must undergo byte order translation when transitioning between the physical memory heap and the operating system's network buffer.

Operating systems expose standard socket library calls to handle this translation:

  • htons(): Host-to-Network Short (16-bit integer conversion, typical for port numbers)
  • htonl(): Host-to-Network Long (32-bit integer conversion, typical for IPv4 addresses)
  • ntohs(): Network-to-Host Short (16-bit integer conversion)
  • ntohl(): Network-to-Host Long (32-bit integer conversion)

CAUTION: LOW-LEVEL C STRUCT CASTING

In languages like C and C++, developers are often tempted to deserialize incoming binary streams by casting the raw byte buffer directly to a struct pointer. This is extremely dangerous. It assumes that the compiler's memory alignment, padding, and host byte order match the incoming network packet exactly. If the compiler introduces padding bytes for alignment (e.g., aligning variables to 4-byte or 8-byte boundaries to prevent slow unaligned memory reads), or if the sender and receiver have mismatching endianness, the parsed struct will contain corrupted fields. Furthermore, unaligned memory accesses can trigger processor-level bus errors, crashing the process immediately.

Varints (Variable-Length Quantized Integers)

Standard integers in modern computer memory occupy a fixed size of 32 or 64 bits (4 or 8 bytes), regardless of their actual value. If a program stores the number 42, a standard 32-bit representation consumes four full bytes of memory: the hidden marker. Sending three leading bytes of pure zeros over a network is incredibly wasteful.

Varints solve this by allowing integers to consume a variable number of bytes depending on their magnitude. Each byte in a Varint uses the Most Significant Bit (MSB)—the 8th bit—as a continuation flag. The remaining 7 bits store the actual numerical payload:

  • If the MSB is set to \(1\), it indicates that more bytes follow in the stream.
  • If the MSB is set to \(0\), it indicates that this is the final byte of the integer.

The following is a step-by-step bitwise mathematical trace of encoding the integer \(300\):

Step 1: The decimal number \(300\) is represented in binary as \(00000001\ 00101100_2\) (9 active bits).

Step 2: Split this binary sequence into groups of 7 bits starting from the least significant bit (right to left):

  • Group 1 (LSB 7 bits): \(0101100_2\) (decimal \(44\))
  • Group 2 (next 7 bits): \(0000010_2\) (decimal \(2\))

Step 3: Set the MSB (the 8th bit) of each group except the final one to \(1\):

  • For Group 1, set the MSB to \(1\), yielding \(10101100_2\) (hexadecimal the hidden marker).
  • For Group 2, since it is the final group, set the MSB to \(0\), yielding \(00000010_2\) (hexadecimal the hidden marker).

Zig-Zag Encoding

Standard Varints have a severe limitation when dealing with negative integers. In standard two's complement arithmetic, negative numbers have their high-order bit set to \(1\). For a 64-bit integer, a negative value like \(-1\) is represented as sixty-four consecutive \(1\)s. If one tries to serialize this using standard Varints, the continuation flag (MSB) remains set to \(1\) for nine full bytes, and the final byte contains the remaining bits, resulting in a ten-byte payload for a tiny negative number!

To solve this, Protobuf employs Zig-Zag Encoding for signed integer types (sint32, sint64). Zig-Zag encoding maps signed integers to unsigned integers by zig-zagging back and forth across zero, such that small negative numbers are converted into small positive numbers:

  • \(0 \to 0\)
  • \(-1 \to 1\)
  • \(1 \to 2\)
  • \(-2 \to 3\)
  • \(2 \to 4\)
  • \(-3 \to 5\)

The bitwise shift and XOR arithmetic formulas are defined as:

\[Z(n) = (n \ll 1) \oplus (n \gg 31) \quad (\text{for } 32\text{-bit})\]
\[Z(n) = (n \ll 1) \oplus (n \gg 63) \quad (\text{for } 64\text{-bit})\]

Note that the right shift \(n \gg 31\) is an arithmetic shift, which replicates the sign bit. Thus, for positive numbers, the shift yields all zeros, and the result is simply \(n \ll 1\) (even numbers). For negative numbers, the shift yields all ones (the hidden marker), and the XOR operation flips all bits, resulting in \(2|n| - 1\) (odd numbers).

Let one trace \(n = -1\) step-by-step:

Step 1: Binary representation of \(-1\) (32-bit two's complement): \(11111111\ 11111111\ 11111111\ 11111111_2\).

Step 2: Left shift by 1: \(11111111\ 11111111\ 11111111\ 11111110_2\).

Step 3: Arithmetic right shift by 31: \(11111111\ 11111111\ 11111111\ 11111111_2\).

Step 4: Bitwise XOR the results:

\[11111111\ 11111111\ 11111111\ 11111110_2 \oplus 11111111\ 11111111\ 11111111\ 11111111_2 = 00000000\ 00000000\ 00000000\ 00000001_2 = 1_{10}\]

This maps \(-1\) to \(1\), which is then serialized using Varint in a single byte!

The decoding math is equally simple and fast:

\[n = (Z \gg 1) \oplus -(Z \ \& \ 1)\]

X. The Unicode Glyph Space: UTF-8 Prefix Bitwise Arithmetic and Dynamic Character Sizing

While text-based serialization standards use characters, the underlying transport layer only understands bits. This translation bridge is governed by Character Encoding Schemes:

  • ASCII: The original 7-bit character encoding, mapping 128 characters to integers \(0\) through \(127\). The 8th bit is always \(0\). Extremely fast to parse because every character is exactly one byte, but it cannot represent any non-English character systems or emojis.
  • UTF-16: A fixed/variable 16-bit character encoding. While it can represent most common characters in two bytes, it introduces massive spatial bloat for Western text (doubling the size compared to ASCII) and introduces severe endianness ambiguity. If systems transmit UTF-16, they must prepend a Byte Order Mark (BOM) like the hidden marker or the hidden marker to specify whether the byte stream is Big-Endian or Little-Endian, adding transport overhead and parsing complexity.
  • UTF-8: Formulated by Ken Thompson and Rob Pike in 1992, UTF-8 is a variable-width, backwards-compatible encoding scheme that has become the universal standard of the web. It uses a brilliant prefix-coding bitmask mechanism to encode all \(1,112,064\) Unicode code points using between 1 and 4 bytes.

When the parser processes a UTF-8 stream, it examines the leading bits of each byte. If a byte starts with \(0\), the parser knows instantly that it is a single-byte ASCII character. If a byte starts with \(110\), the parser knows that a 2-byte sequence has begun, and it must verify that the next byte starts with \(10\) (the continuation prefix). If the next byte does not start with \(10\), or if a character is represented using more bytes than mathematically required (an Overlong Encoding), the parser must reject the stream as invalid to prevent critical security vulnerabilities.

SECURITY: OVERLONG UTF-8 ENCODINGS

An overlong encoding occurs when a character is serialized using more bytes than necessary (e.g., encoding the ASCII character "/" as 0xC0 0xAF instead of the standard the hidden marker). If a Web Application Firewall (WAF) or validation filter scans the stream looking for dangerous characters like / or < using simple ASCII matching, it will miss the overlong representation. If the downstream parser subsequently deserializes the overlong bytes back into standard ASCII, the security checks are completely bypassed, enabling Directory Traversal and Cross-Site Scripting (XSS) attacks. Security-minded parsers must strictly validate that all Unicode characters are encoded in their shortest possible form.

XI. The Ancient Compiler: Paninian Generative Grammar, Shiva Sutras, and Ashtadhyayi as the First Formal Lossless Serialization Engine

The formalization of generative grammatical rules and structured translation did not begin with modern computer science. It was fully realized in the 4th century BC in Gandhara (modern-day Pakistan) by the ancient grammarian Panini in his monumental work, the Ashtadhyayi. Panini formulated a highly formal, algebraic Sanskrit grammar that operates as the world's first formal, lossless code serialization and generative state machine, establishing the foundations of linguistic structure and computational parser design.

To compress and serialize the phonetic structure of Sanskrit, Panini compiled the Shiva Sutras—an ordering of the phonemes of the language in fourteen distinct verses. Each verse terminates with a special non-phonemic marker sound (an it or anubandha).

This arrangement functions as a highly optimized algebraic indexing table. By selecting a starting sound from the Shiva Sutras and pairing it with a subsequent marker sound, one creates a Pratyahara—a compact shorthand abbreviation representing a specific class of sounds.

To illustrate this phonetic indexing, consider the first four Shiva Sutras:

  1. a i uṇ
  2. ṛ ḷk
  3. e oṅ
  4. ai auc

The pratyahara ac is formed by taking the first sound a from the first sutra, and the marker sound c from the fourth sutra. It represents all vowels in this range, excluding the marker sounds (ṇ, k, ṅ, c). Thus, ac represents:

\[\text{ac} = \{a, i, u, \underline{r}, \underline{l}, e, o, ai, au\}\]

This is functionally identical to modern regular expression character classes (like [a-z] or the resource address) or bitmasks used to identify groups of token primitives inside lexical analyzers.

The Ashtadhyayi as a Generative State Machine

The core of the Ashtadhyayi consists of approximately 4,000 algebraic rules (sutras) designed to operate as a completely deterministic generative state machine. The input to the system is an abstract semantic graph of intent (consisting of root concepts, tense descriptors, case relations, and grammatical markers). The rules of the Ashtadhyayi are applied to this graph in a deterministic sequence of state transitions, resolving overlaps and collisions using prioritization rules, ultimately flattening the rich semantic structure into a single, highly compressed phonetic serial stream of spoken speech.

To prevent sound collisions at boundaries, Panini formulated Sandhi Rules. These function exactly like low-level compiler optimization passes that compress boundary tokens to achieve maximum transmission efficiency.

A classic example is the Sandhi rule iko yaṇ aci (Ashtadhyayi Rule 6.1.77):

\[ik \to ya\text{ṇ} \quad / \quad \_\_ ac\]

This rule states that a character from the ik group (\(i, u, \underline{r}, \underline{l}\)) is replaced by its corresponding character of the yaṇ group (\(y, v, r, l\)) when followed by any vowel (the ac group), provided the following vowel is not homogenous.

  1. The terminal vowel \(i\) belongs to the ik group.
  2. The following vowel \(\bar{a}\) belongs to the ac group.
  3. The corresponding yaṇ replacement character for \(i\) is \(y\).
  4. The engine replaces the terminal \(i\) of "iti" with \(y\), resulting in the compressed, flattened serial output: ityāha.
