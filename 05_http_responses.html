Chapter the Fifth

HTTP Responses & Status Codes

"The five numbers that rule digital systems, how a homing pigeon solved conditional caching in medieval France, and why 404 is the most existential statement a computer can make."
♦ ✦ ♦

In the year 1342, the Abbot of Saint-Denis in France faced an administrative crisis. He was compiling a library of theological manuscripts, but his scribes were working from older, potentially corrupted translations. He wanted to verify if his copy of the City of God by Saint Augustine matched the authoritative papal manuscript preserved in the Vatican.[1]

The Abbot had two choices. He could pack the entire twenty-two books onto a mule, assign armed monks to guard it, and spend four months crossing the Alps to Rome to compare the texts line by line. This was slow, expensive, and dangerous. This is the Unconditional Transfer Problem—sending an entire dataset down a high-latency transport line.

Instead, the Abbot used a smarter approach. He ordered his head scribe to compile a short, unique signature of the manuscript—the first letter of every paragraph, stamped with the abbey's wax seal. They tied this tiny parchment to a homing pigeon and released it toward Rome.

When the pigeon landed in the Vatican courtyard, the papal librarian pulled down the authoritative manuscript, ran the same extraction, and compared the two seals. If the seals matched, he did not copy the thousand-page manuscript. Instead, he stamped a single blue mark—"Not Modified"—tied it to the pigeon, and sent it back.

The Abbot looked at the blue mark and knew, with certainty, that his local copy was perfectly in sync with the sovereign copy in Rome. He had verified a massive dataset across a thousand miles using nothing more than a pigeon, a wax seal, and a three-digit equivalence check. This is the exact logical blueprint of HTTP Validation Caching using ETags.

Consider a second analogy: the Heraldic Calls of the Holy Roman Empire. When the Emperor's herald rode into a provincial town to deliver a decree, he blew a silver trumpet and announced a standardized numeric call:

  • 1xx: "Hold on, the court is deliberating. Stand by."
  • 2xx: "Your petition has been granted. Here is the permit."
  • 3xx: "The registry has moved to Nuremberg. Go there."
  • 4xx: "Wrong form, or you lack the proper seal. Fix it."
  • 5xx: "The castle walls have collapsed. We cannot process this."

The townspeople did not need to read the entire scroll to understand what to do. The first digit determined their entire course of action. In the digital world, HTTP Responses are these formal heraldic calls. When a server replies, it wraps the response in a strict three-part envelope: the Status Line, the Metadata Headers, and the optional Payload Body. And the most critical marker is the three-digit Status Code.[2]

1. How an HTTP Response Is Structured

Every HTTP response is composed of three parts sent in strict order: the Status Line (which includes the status code), the Headers (metadata about the response), and the optional Body (the actual data). The headers and body are separated by a blank line.

The response travels over TCP, which is a stream protocol—it delivers bytes in order but does not preserve message boundaries. So the HTTP format itself defines where one response ends and the next begins, using consistent line breaks and the Content-Length header (or chunked encoding) to mark the body's boundaries.

Chunked Transfer Encoding

Sometimes the server does not know the total size of the response before it starts sending—like when streaming results from a large database query in real time. In these cases, the server uses Chunked Transfer Encoding. Instead of declaring the full size upfront, it sends the data in a series of numbered chunks, each prefixed with its own size. A zero-length chunk signals the end of the response.

This allows the server to begin streaming data as soon as the first row of results is available, drastically reducing the time the client waits for the first byte. If something goes wrong mid-stream (like a database connection dropping), the server cannot change the already-sent status code—it simply terminates the connection, and the client recognizes the response as incomplete.

CAUTION A server must never send both a Content-Length header and a Transfer-Encoding: chunked header at the same time. This contradiction can create security vulnerabilities. Frameworks should automatically strip Content-Length when streaming chunked responses.

The Mughal Farman: A Structural Analogy

This rigid serialization structure mirrors the Mughal Empire's royal decree system. A Farman had distinct zones that worked like an HTTP response:

  • The Tughra (ornate calligraphic header): Like the Status Line—it established authority and signaled the document was genuine.
  • The Unwan (decorated border panel): Like the Headers—it declared the decree's type and scope, allowing clerks to route it to the right department without reading the full text.
  • The Muhr-i-Khas (dynastic signet seal): Like a cryptographic ETag—regional governors verified the decree by comparing the seal against an authoritative matrix preserved locally, without sending a courier back to Delhi.

2. The Five Classes of Status Codes

The three-digit status code tells the client exactly what happened. The first digit determines the category; clients evaluate these codes using decade-based logic.

Plate XI: The Symmetrical Hierarchy of Royal Decrees

1xx: Informational

These are intermediate responses that signal the server is still processing. They do not complete the transaction—the client must keep the connection open and wait for a final response.

100 Continue

This status prevents clients from wasting bandwidth on requests that will be rejected. When a client wants to send a large payload (like a multi-gigabyte file upload), it first sends just the headers with an Expect: 100-continue directive and waits. The server checks the headers—authentication, size limits, content type—and either sends 100 Continue to greenlight the upload, or rejects the request immediately with a 401 or 413 error. This saves massive bandwidth when requests would fail anyway.

When a proxy like NGINX sits between client and server, it can be configured to handle this check locally, avoiding the round-trip to the upstream application entirely.

101 Switching Protocols

This is the gateway to real-time, bidirectional communication. Standard HTTP is one-way: the client asks, the server responds, done. For live trading dashboards, multiplayer games, or chat apps, this model is inadequate.

To upgrade, the client sends a standard HTTP GET request with Upgrade: websocket and a Connection: Upgrade header, along with a randomly generated key. If the server supports WebSockets, it performs a cryptographic handshake—computing a hash from the client's key combined with a fixed magic string—and sends back 101 Switching Protocols.

At this point, the HTTP request-response cycle is dissolved. The connection is handed off from the short-lived HTTP handler to a persistent WebSocket controller. The protocol switches from text-based HTTP to binary frames. Because WebSocket connections stay open indefinitely, servers use event-driven architectures (monitoring thousands of connections on a single thread) to handle the load without allocating a thread per socket.

2xx: Success

The request was received, understood, and processed successfully.

200 OK

The universal success response. The requested resource is in the response body. Used for successful reads (GET), and updates that return data (PUT, POST).

201 Created

Returned when a new resource has been successfully created—typically after a POST request. The server commits the new record to the database before sending this response. It must include a Location header pointing to the newly created resource, such as Location: /v1/users/402.

202 Accepted

The foundation of asynchronous processing. When a client requests a heavy operation—rendering a 3D model, generating a large report, processing a video—completing it synchronously would hold the connection open for minutes, risking timeouts.

Instead, the server validates the request, queues the task in a background job system, and immediately returns 202 Accepted with a job tracking ID. The client can then poll a status endpoint to check progress. Once the task finishes, the status endpoint redirects the client to the completed result.

204 No Content

A successful response with an empty body. Used for DELETE operations or updates where returning the resource state would be redundant. The body must be completely empty—not even a blank JSON object. Including any body content violates the HTTP specification and can confuse the client's parser on persistent connections, causing it to misinterpret the bytes as the start of the next response.

3xx: Redirection

Redirection tells the client to look for the resource at a different address. The distinction between codes has significant consequences for browser caching, SEO, and request integrity.

Status Code Type Caching Method Preservation SEO Impact
301 Moved Permanently Aggressive (cached indefinitely) No (changes POST to GET) Transfers ~95% link equity
302 Found (Temporary) None No (changes POST to GET) None
307 Temporary Redirect None Yes (preserves method and body) None
308 Permanent Redirect Aggressive (cached indefinitely) Yes (preserves method and body) Transfers ~95% link equity

301 vs. 308: Permanent Redirects

A 301 Moved Permanently tells browsers and search engines that the resource has a new permanent home. Search engines transfer the accumulated authority of the old URL to the new one.

However, the original 301 specification had a flaw: if a client sent a POST request and received a 301, the browser would silently convert it to a GET on retry, dropping the request body entirely. The modern 308 Permanent Redirect fixes this by strictly requiring the client to preserve the original method and body.

Both codes cause browsers to cache the redirect aggressively—often permanently. Deploying a permanent redirect by mistake is extremely difficult to undo, since browsers will not re-check the original URL. For active migrations, it is safer to start with temporary redirects (302/307) and switch to permanent ones only after confirming the routing is correct.

302 vs. 307: Temporary Redirects

Temporary redirects tell the client that the resource is temporarily elsewhere, but the original URL should still be used for future requests. No search equity is transferred. The same method-preservation distinction applies: 302 allows method mutation, while 307 strictly preserves it.

4xx: Client Errors

The client's request was invalid. The server is rejecting the transaction because the client violated the system's rules.

400 Bad Request

A general error for malformed requests—the JSON is broken, URL parameters failed validation, or required headers are missing.

401 Unauthorized vs. 403 Forbidden

These two are commonly confused, but the distinction is critical for security.

A 401 Unauthorized (more accurately "Unauthenticated") means the server cannot verify who you are. The token is missing, expired, or has an invalid signature. The response must include a WWW-Authenticate header telling the client what credentials are needed. Sending a new, valid token may resolve the issue.

A 403 Forbidden means the server knows exactly who you are—and you are not allowed in. Your identity was verified, but your role or permissions are insufficient. Logging in again will not help.

404 Not Found

The server cannot find a resource matching the requested URL. The router searched its path patterns and found no match. Modern routers also use this to block directory traversal attacks—any path attempting to escape the resource root (using sequences like ../) is normalized, caught, and rejected with a 404.

429 Too Many Requests

The client has exceeded their rate limit. Servers implement rate limiting using algorithms like the Token Bucket: each client gets a bucket with a maximum capacity of tokens, refilled at a steady rate. Each request consumes one token. If the bucket empties, subsequent requests are rejected with 429 until tokens refill.

In production, rate limiting is typically handled by an in-memory store like Redis to ensure the check is fast and consistent across distributed servers. The response should include a Retry-After header telling the client how many seconds to wait.

5xx: Server Errors

The client's request was valid, but the server failed to process it.

500 Internal Server Error

A catch-all for unexpected crashes—null pointer exceptions, database connection failures, unhandled bugs. Production servers must never leak raw stack traces or database schema details in the response; this is a serious security vulnerability that exposes internal architecture to attackers.

Instead, resilient backends catch all uncaught exceptions, log the full error details to an observability system with a unique tracking ID, and return a clean, generic error message to the client with that ID for support reference.

502 Bad Gateway

A proxy or load balancer tried to reach the upstream application server, but the upstream was offline or returned a corrupted response. This typically means the application process has crashed or its connection queue is exhausted. Administrators can prevent this by tuning the operating system's connection backlog limits.

503 Service Unavailable

The server is temporarily unable to handle requests—usually due to maintenance or overload. To prevent cascading failures, backends use the Circuit Breaker pattern, which operates in three states:

  1. Closed: Healthy. Requests pass through normally.
  2. Open: Failing. Requests are immediately rejected with 503, giving upstream services time to recover.
  3. Half-Open: A small test batch of requests is allowed through to check if the system has recovered.

Load-shedding systems monitor CPU, memory, and thread usage. When thresholds are exceeded, they proactively drop low-priority requests at the gateway boundary to prevent total system collapse.

504 Gateway Timeout

The proxy waited for the upstream server to respond, but it took too long (typically 30–60 seconds). This usually points to a slow database query, a table deadlock, or an unresponsive external API. Application architectures should enforce their own execution timeouts—halting slow queries and rolling back cleanly rather than letting the proxy kill the connection abruptly.

3. Caching: Freshness, Validation, and State Machines

HTTP caching stores copies of server responses close to the user—in the browser's disk cache, ISP routers, or global CDN edge nodes—to avoid the slow, expensive round-trip to the origin server every time.

Freshness Caching (Cache-Control)

The Cache-Control header tells clients how long they can use a cached response without asking the server:

  • public, max-age=31536000: Any cache (browser, proxy, CDN) may store this for one year. Used for static files with unique hashes in their filenames, like bundle.87a1b3.js.
  • private, no-cache: The browser may cache it, but must check with the server before using it.
  • no-store: Nothing may be written to disk. Used for sensitive data like bank records or credentials that should exist only in temporary memory.
  • stale-while-revalidate=60: The browser may serve a stale cached version immediately while quietly fetching a fresh copy in the background. This eliminates visible loading delays.

Conditional Validation (ETags and Last-Modified)

When a cached response expires or no-cache is set, the browser does not need to re-download the full file. Instead, it sends a conditional request with a validator:

  • ETag: A unique hash of the file's content (like a fingerprint). The browser sends it back as If-None-Match: "hash-9283".
  • Last-Modified: The timestamp of the file's last change. The browser sends it as If-Modified-Since.

The server compares the validator against its current resource. If nothing has changed, it returns 304 Not Modified with an empty body—the browser uses its cached copy. This is exactly like the Abbot's pigeon: the wax seals match, so no thousand-page manuscript needs to travel.

Plate XII: ETag Validation & Conditional Requests

The Cache Lifecycle

A cached response moves through three states:

  1. Fresh: The cached response is still within its max-age window. The browser serves it instantly with no network request.
  2. Stale: The max-age has expired. The browser must send a conditional request to the server to check if the resource has changed.
  3. Stale-While-Revalidating: If stale-while-revalidate is set, the browser serves the stale copy immediately while fetching an update in the background. If the server confirms nothing changed (a 304), the cache resets to Fresh.

The apparent age of a cached asset is simply: the current time minus the time the server originally sent the response. If this age is less than max-age, the cache is Fresh. Once it exceeds max-age, the client must validate.

The Distributed Cache of Mauryan Rest Houses

This cache validation architecture was implemented in ancient India through the imperial post system established under Kautilya's Arthashastra during the Maurya Empire. The central court in Pataliputra distributed copies of imperial decrees to regional rest houses (Sattras) along major trade routes. These acted as distributed cache nodes.

When a merchant arrived at a provincial checkpoint, the regional officer matched their royal signet ring against the decree cached locally. If the seals matched, transit was approved—a 304 from cache. Only when the seals did not match was a runner dispatched to Pataliputra for a fresh copy, ensuring rapid administration with minimal transport overhead.

4. Content Negotiation & Security Headers

Response headers govern how the browser interprets, secures, and caches the payload.

Content Negotiation and the Vary Header

Clients express their preferences through headers like Accept (preferred format), Accept-Encoding (supported compression), and Accept-Language (preferred language). The server selects the best match and responds accordingly.

If a resource's representation varies based on these request headers, the server must include a Vary header, such as Vary: Accept-Encoding. This tells CDN proxies that the cache key is not just the URL—it must also account for the client's encoding preference. Without this, a proxy might cache a compressed Brotli response and serve it to a legacy browser that cannot decompress it, resulting in garbled output.

Security Headers

Modern backends must attach a strict set of security headers to every HTML response:

  1. Content-Security-Policy (CSP): Restricts where the browser can load scripts, styles, and images from. A default-src 'self' directive blocks external injections by default. A cryptographic nonce ensures only explicitly authorized inline scripts execute, neutralizing injected attacks.
  2. Strict-Transport-Security (HSTS): Forces all future requests to use HTTPS instead of HTTP, blocking SSL-stripping attacks. A max-age of two years locks the browser into secure mode.
  3. X-Content-Type-Options: nosniff: Prevents the browser from guessing a file's type. A malicious image file containing hidden JavaScript will not be executed.
  4. X-Frame-Options: SAMEORIGIN: Blocks clickjacking by preventing the page from being embedded inside an iframe on other websites.
  5. Referrer-Policy: strict-origin-when-cross-origin: Strips sensitive URL parameters from the Referer header when navigating from a secure site to an insecure one, protecting user privacy.

5. Cross-Origin Resource Sharing (CORS)

Browsers enforce the Same-Origin Policy, which prevents JavaScript on one domain from reading data from another. A script running on https://example.com cannot read responses from https://api.bank.com. This is a critical security boundary.

CORS is the protocol that safely permits cross-domain communication when needed—like a frontend app on one domain querying an API on another.

Simple vs. Preflight Requests

Simple requests (basic GET, POST, or HEAD with standard headers) are allowed through directly. But "non-simple" requests—those using custom headers like Authorization or methods like PUT/DELETE—trigger a Preflight.

The browser automatically sends an OPTIONS request first, asking the server: "Do you allow this origin to make this type of request?" The server checks its trusted origins whitelist and responds with the allowed methods, headers, and whether credentials are permitted. The browser caches this approval for the duration specified in Access-Control-Max-Age, avoiding repeated preflight checks.

SECURITY Setting Access-Control-Allow-Origin: * together with Access-Control-Allow-Credentials: true is strictly forbidden. It would let any website make authenticated requests on a user's behalf. The server must validate the Origin header against a trusted whitelist and echo it back only if it matches.

Kautilya's Gatekeeping and CORS

This origin validation mirrors the defensive security of Mauryan fortified cities (Durgas). When a traveler approached the city gate, the gatekeeper (Gopura) halted them and demanded their official signet ring (Mudra) and passport (Patra). The gatekeeper checked the traveler's origin: were they from allied territory or an unauthorized domain? Only when valid credentials were presented was the gate opened—just as a CORS preflight validates the origin before allowing cross-domain access.

6. Compression: Making Responses Smaller

To speed up page loads worldwide, servers compress their responses before sending them. Compression works by finding and eliminating redundancy in data—replacing repeated patterns with compact references.

Gzip

Gzip (using the DEFLATE algorithm) works in two passes. First, it scans for repeated sequences of characters and replaces duplicates with small reference pointers. Then, it assigns shorter bit representations to the most common characters. This works well for larger files, but for small responses (like a 150-byte JSON payload), the overhead of the compression metadata can actually make the result larger than the original.

Brotli

Brotli, developed by Google, takes a smarter approach. It ships with a massive pre-built dictionary containing over 13,000 common web substrings—things like </div>, display: block, and application/json—shared between all modern browsers and servers.

When Brotli encounters a substring matching this dictionary, it replaces it with a compact index reference. Because the dictionary is pre-shared, no per-response overhead is needed to describe common patterns. This allows Brotli to compress HTML, CSS, and JavaScript 20–30% more effectively than Gzip, meaning fewer packets and faster page loads.

7. The "200 OK with Error" Anti-Pattern

One of the most destructive mistakes in modern API design is returning an HTTP 200 OK status code with a JSON body that describes an error:

Status: 200 OK, but the body says {"success": false, "error": "database_connection_failed"}

This is a serious architectural failure that breaks the assumptions the entire web infrastructure relies on.

To understand why, consider the late Mughal Empire. As central authority weakened, provincial treasuries began acting independently. The emperor would issue a royal decree—a Farman—stamped with the imperial seal, formally declaring that a merchant was granted funds from the Bengal treasury. The Farman carried all the visual indicators of absolute validity.

Yet when the merchant traveled to the treasury in Murshidabad and presented the Farman, the local clerk would examine the seal, nod respectfully, and quietly inform him the treasury was empty. The Farman was a "200 OK" from the central authority, but the actual result was failure.

In software, the consequences are immediate and mechanical. Network devices—reverse proxies, CDNs, load balancers, and monitoring systems—make decisions by reading only the status code, not by parsing the response body. If a server returns 200 OK for a database outage, here is what happens:

  • CDN caches the error: A proxy that caches 200 OK responses will store the error message and serve it to millions of subsequent visitors.
  • Monitoring goes blind: Observability tools track system health by counting 5xx and 4xx responses. If errors hide behind 200 OK, dashboards show a perfect 100% success rate while the system is on fire.
  • Proxies cannot act: Load balancers and API gateways cannot retry failed requests, redirect traffic, or trigger circuit breakers because the status code says everything is fine.

The HTTP status code is a contract with the entire network infrastructure. If a resource does not exist, return 404. If the application crashed, return 500. If rate-limited, return 429. Do not lie to the network.

8. Chapter Summary

The HTTP response protocol is the formal treaty governing all server-to-client communication. By enforcing strict status codes, leveraging conditional caching with ETags, applying compression, and setting robust security headers, applications maintain reliability and speed at scale.

The fundamental rule: the status code must always reflect the truth of what happened. Intermediate proxies, CDNs, monitoring systems, and client applications all depend on this contract. A server that lies in its status code breaks the chain of trust that makes the modern web functional.
