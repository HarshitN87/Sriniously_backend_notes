Chapter the Fourth

HTTP Methods & The Same-Origin Borders

"GET, POST, and the delicate art of persuading the browser that your local server is not a compromised state actor trying to steal your bank cookies."
♦ ✦ ♦

Consider the physical act of signing a document. On a mechanical level, dragging a pen across paper is just friction and ink. But the semantic verb attached to that act determines its real-world impact.

If you sign a wedding guest book, you are making a passive record. This is a GET. If you sign a bank check, you are creating a financial instrument that moves money. This is a POST. If you sign a new will to replace an old one, you are executing a complete overwrite. This is a PUT. If you cross out a single typo in a contract, you are making a partial update. This is a PATCH. If you sign a deed of release to cancel a debt, you are executing a deletion. This is a DELETE.

To the paper, it is all just ink. But to the systems relying on that paper, the verb is everything. If a bank check is treated like a guest book and signed twenty times, bankruptcy follows. This distinction brings us to two vital concepts in backend engineering: Semantic Verbs and Idempotency.

Think of an Elevator Button vs. a Slot Machine Lever. Pressing the "5" button in an elevator is an idempotent operation. Pressing it once takes you to the fifth floor. Pressing it ten more times doesn't take you to the fiftieth floor, nor does it charge you ten times. The final state remains exactly the same.

Contrast this with a slot machine lever. Each pull is a non-idempotent operation. Pull it once, you spend one coin. Pull it three times, you spend three coins. The state changes with every single action. If a network glitch causes your request to be sent multiple times, you need to know whether the system will safely ignore the duplicates or process them all.

I. The Nature of State: Permanent Records vs. Daily Logs

Ancient empires faced the exact same coordination challenges we do today. They needed to distinguish between permanent, unchangeable records and daily, mutable logs.

For example, royal decrees granting land or tax exemptions were engraved on heavy copper plates. These were permanent, idempotent records. Reading the plate a hundred times didn't change the land ownership. If the grant was revoked, a new decree was issued to wipe the record clean. This mirrors modern idempotent methods like PUT and DELETE.

In contrast, daily tax collections and market transactions were written on fragile palm leaves. These were non-idempotent, append-only logs. If a scribe accidentally recorded a tax payment twice, the ledger was corrupted, and the state was mutated. This mirrors modern non-idempotent methods like POST and PATCH.

Understanding this distinction reveals why modern software systems must partition their actions. When a client communicates with a server across the chaotic internet, the server must know whether the request is a permanent, safe command that can be repeated without consequence, or a dynamic transaction that must be guarded against duplicates.

II. REST vs. RPC: Nouns vs. Verbs

To build reliable distributed architectures, a fundamental decision must be made regarding how client intentions map to network coordinates. This splits the engineering world into two paradigms: Remote Procedure Call (RPC) and Representational State Transfer (REST).

In an RPC architecture, the URL represents an action. The API paths look like verbs: creating a user, deleting a user, or updating a user. The HTTP protocol is treated as a dumb transport pipe, almost exclusively using the POST method to trigger remote execution. While intuitive, this creates massive coordination challenges as systems scale, because caching and routing tools cannot easily understand what the endpoints actually do.

REST completely reverses this paradigm. Under the REST model, the network interface is structured around nouns—stable, unique resources. The URL path identifies the resource, not the action. To perform an action on that resource, the developer changes the HTTP method verb at the protocol level.

To read a user, a GET request is sent. To completely replace the user, a PUT request is sent. To delete the user, a DELETE request is executed. This clean decoupling separates resource identification from state mutation, allowing the network infrastructure (proxies, gateways, CDNs) to reason about the request's semantics and optimize caching automatically.

REST is built on six core constraints:

  1. Client-Server: The user interface and data storage are separated, allowing each to scale independently.
  2. Statelessness: Each request contains all the information needed to process it. The server does not store session state in memory.
  3. Cacheability: Responses explicitly define whether they can be cached, improving network efficiency.
  4. Uniform Interface: A globally consistent vocabulary of nouns and verbs, ensuring resources are uniquely identified and messages are self-describing.
  5. Layered System: The architecture is hierarchical. A client cannot tell if it is connected directly to the end server or an intermediate proxy.
  6. Code-on-Demand (Optional): Servers can temporarily extend client capabilities by transferring executable scripts.

III. The Seven HTTP Verbs

The HTTP protocol defines a small, highly specialized vocabulary of verbs. Each verb carries a distinct set of operational guarantees regarding safety, idempotency, and caching.

Method Safe? Idempotent? Request Body? Response Body? Preflight Trigger? Database Lock Level
GET ✅ Yes ✅ Yes ❌ No ✅ Yes ❌ No None (Shared Read)
HEAD ✅ Yes ✅ Yes ❌ No ❌ No ❌ No None (Metadata Only)
POST ❌ No ❌ No ✅ Yes ✅ Yes ❌ No Exclusive Row Write / Insert
PUT ❌ No ✅ Yes ✅ Yes ✅ Yes ✅ Yes Exclusive Write / Overwrite
PATCH ❌ No ❌ No (Usually) ✅ Yes ✅ Yes ✅ Yes Exclusive Row Lock (Update)
DELETE ❌ No ✅ Yes ❌ No ✅ Yes ✅ Yes Exclusive Write / Tombstone
OPTIONS ✅ Yes ✅ Yes ❌ No ✅ Yes ❌ No None (Capability Query)

1. GET & HEAD: The Passive Observers

A GET request is designed strictly to read a representation of a resource. It must be "Safe," meaning it does not alter the resource's state on the server. Because it is safe and idempotent, the entire web infrastructure is optimized to cache its responses. Browsers, intermediate proxies, and global CDNs all cache GET requests to save bandwidth and reduce server load.

The HEAD method is identical to GET, with a single critical optimization: the server compiles the exact same headers but is strictly forbidden from returning the response body. It is the ultimate metadata probe. If a client needs to download a massive dataset, it can first dispatch a HEAD request to check the file size or verify if its local cache is still valid, without wasting bandwidth on the actual payload. Search engines use this extensively to manage their crawling budgets.

2. POST: The Generator of State

POST is the ultimate non-idempotent verb. It is designed to submit an entity to a target resource, causing the server to create a new resource or execute a complex process (like a financial transaction). Every time a client sends a POST request, the server is expected to execute a new database insert or deduct funds. Because it is non-idempotent, browsers will aggressively warn users if they attempt to refresh a page generated by a POST request to prevent accidental duplicate transactions.

3. PUT vs. PATCH: The Complete Overwrite and the Surgical Strike

One of the most common architectural mistakes in API design is the misuse of PUT and PATCH. Both update an existing resource, but their contracts are fundamentally different.

PUT is defined as a complete resource replacement. If a user resource has twenty fields, and the client only wishes to update the phone number, a PUT request must still carry all twenty fields in the request body. If the client omits a field, the server assumes the client wishes to erase it. Because it completely overwrites the target resource with the exact same dataset, it is mathematically idempotent.

PATCH was introduced to resolve this inefficiency by enabling partial, differential updates. With a PATCH request, the client only transmits the specific fields it wishes to mutate. The server dynamically updates only those target columns. However, because a PATCH request modifies existing state based on instructions (like "increment this counter"), it is not guaranteed to be idempotent. Sending the same increment instruction three times will increment the counter by three.

In dynamic environments, concurrent partial writes present a high risk of the Lost Update Problem, where two clients overwrite each other’s data. To resolve this, backends implement Optimistic Concurrency Control using ETags (Entity Tags). When the client reads the resource, the server returns a version tag. When the client sends the update, it includes this tag in the request headers. If the tag doesn't match the current version in the database, the server rejects the update, forcing the client to fetch the latest data and try again.

IV. Idempotency in Unreliable Networks

In a theoretically perfect network, the distinction between idempotent and non-idempotent methods is trivial. But physical networks are fundamentally chaotic. They are subject to hardware failures, routing reconfigurations, and signal dropouts.

Suppose a client dispatches a non-idempotent request (like a billing instruction) across a lossy network. The server successfully processes the payment, but the return path drops. The server returns a success response, but the packet is lost in transit. From the client's perspective, the request timed out. The client cannot distinguish between a request that was lost before reaching the server, and a request that succeeded but lost its response.

To recover, the client must retry the request. If the system does not enforce idempotency, the server will process the duplicate request, leading to a catastrophic double-billing event.

To eliminate this error, the system must project an idempotent interface onto the non-idempotent transition. This is achieved by introducing a Deduplication State Ledger, typically implemented using a high-performance distributed key-value store like Redis.

The sequence operates as follows:

  1. The client generates a unique, single-use identifier (an Idempotency Key) and attaches it as an HTTP header.
  2. The server receives the request and immediately attempts an atomic operation in Redis using the key. The cache guarantees that the key will only be set if it does not already exist, and sets a time-to-live to prevent memory exhaustion.
  3. If the cache returns a success (a cache miss), the server obtains the lock and proceeds to execute the core database transaction.
  4. Upon successful execution, the server updates the cache key with the computed response body and HTTP status code.
  5. If the connection drops before the client receives the response, the client retries the identical request carrying the same Idempotency Key header.
  6. The server attempts the same cache operation. Because the key already exists, the cache rejects the write. The server blocks any database access, reads the cached payload directly, and returns it instantly to the client.

A critical failure mode occurs if the cache successfully writes the lock, but the primary database transaction subsequently rolls back. If the client retries, the server reads the success response from the cache and hands it back, even though the database write failed. To resolve this, the backend must use an Idempotency Key table inside the primary SQL database itself, committing the idempotency key and the database mutations within the exact same database transaction block. This ensures the lock state and the business ledger succeed or fail together.

V. The Same-Origin Policy and Browser Isolation

While the backend server enforces mathematical state safety through idempotency keys, the browser client must enforce safety through strict spatial isolation boundaries. The primary security boundary of the web is the Same-Origin Policy (SOP).

SOP dictates that a script executing on one origin is strictly forbidden from accessing, reading, or mutating resources loaded from a different origin. An Origin is strictly defined by three components: the Protocol (like HTTP or HTTPS), the Host (the domain name), and the Port number. If any of these three variables differ, the resources are cross-origin.

Under pure SOP, the browser allows Website A to send a request to Website B, but it strictly blocks the script running on Website A from reading the returned response. Without this policy, a malicious site could run background fetches to pull user session cookies or scrape private balances.

SECURITY

CORS is strictly a client-side browser enforcement. It does not act as a server firewall. A terminal tool or a backend script bypasses CORS entirely. The backend server will execute the query; it is the browser that intercepts the response and blocks JavaScript from reading it.

To defend against advanced hardware-level attacks (like speculative execution bugs such as Spectre), modern browsers enforce Site Isolation. When a browser navigates to a new origin, it spawns a dedicated OS-level rendering process. If Website A contains an iframe pointing to Website B, the nested frame is rendered in a completely separate process.

This process-level isolation relies on the Operating System Kernel's virtual memory subsystem. The physical RAM pages allocated to Website A's process are completely unmapped in the page tables of Website B's process. If a compromised renderer process tries to forge a pointer to a physical memory address belonging to another origin, the CPU triggers a hardware page fault instantly, and the OS terminates the rogue process. Thus, the Same-Origin Policy is not merely a high-level JavaScript constraint; it is a legally binding contract enforced by physical transistor states and OS-level virtual memory rings.

VI. CORS and Cross-Origin Security

While the Same-Origin Policy is crucial for security, it created significant barriers for early developers who needed to split their architectures. If a frontend is hosted on one domain and the API lives on another, they represent different origins. Pure SOP would block the frontend from reading any JSON returned by its own API.

To resolve this, early developers bypassed the boundary using JSONP (JSON with Padding). JSONP exploited a deliberate loophole in SOP: the browser allowed HTML script tags to load external JavaScript libraries from any origin. The backend would wrap the raw JSON inside a JavaScript function call and return it. However, JSONP is highly insecure, strictly limited to GET requests, and exposes the application to severe Cross-Site Scripting (XSS) takeovers.

To replace JSONP, the W3C formalized Cross-Origin Resource Sharing (CORS). CORS is a structured negotiation protocol that uses HTTP headers to allow servers to declare which origins are authorized to access their resources.

1. The Preflight OPTIONS Handshake

If CORS only checked permissions after receiving a response, a catastrophic problem would occur for state-mutating requests. Suppose a script on a malicious site executed a request to delete a bank account. Under raw SOP, the browser would dispatch the request, the bank server would delete the account, and only then would the browser block the script from reading the success response. The damage is already done.

To prevent this, the browser executes a Preflight Request before launching any "non-simple" requests (which includes PUT, DELETE, PATCH, or any request with custom headers).

The preflight interaction is executed as follows:

  1. Before sending the actual request, the browser automatically dispatches a silent preflight check using the OPTIONS verb. It carries metadata headers asking for permission to send the specific method and content type.
  2. The server receives the OPTIONS request. It checks its origin permissions without executing any core transaction logic. It returns a response containing the CORS allowances.
  3. The browser reads the preflight response. If the origin and method are permitted, the browser immediately dispatches the actual request carrying the data payload. If the preflight check fails, the browser blocks the actual request from ever hitting the wire, keeping the server safe.

2. Verb Tunneling and CORS Security Risks

While CORS and SOP provide a robust boundary, developers frequently bypass these mechanisms through structural misconfigurations, introducing critical security flaws.

HTTP Verb Tunneling is a technique designed to bypass restrictive firewalls that block non-standard HTTP methods. If a corporate proxy only permits GET and POST traffic, clients wrap their state-mutating requests inside a standard POST request and use an override header. On the server side, middleware intercepts the incoming request, reads the override header, and rewrites the request method internally before routing it.

SECURITY

Verb Tunneling completely nullifies method-based firewall rules. If a security team configures a Web Application Firewall to block all incoming DELETE methods, an attacker can bypass the block by tunneling the deletion within a benign POST envelope carrying the override header.

A second, even more pervasive exploit occurs due to Dynamic Origin Reflection in CORS. When an API needs to support credentials across origins, the CORS specification enforces a strict rule: if a request carries credentials, the server must not return a wildcard in the origin header. It must explicitly name the allowed domain.

To bypass this restriction, developers frequently implement an insecure shortcut. The backend reads the incoming Origin header directly from the client request and echoes it back in the response. This completely neutralizes the protection of the Same-Origin Policy, creating a global CORS bypass that allows any malicious domain to execute authenticated cross-origin requests and read private user payloads.

SECURITY

CORS headers do not prevent Cross-Site Request Forgery (CSRF) attacks. A state-mutating request sent from a malicious origin is still processed and executed by the backend server. The browser's CORS engine only intercepts the response, blocking the script from reading the returned JSON. To defend against CSRF, backends must implement anti-CSRF tokens or use the SameSite cookie attribute.

To defend against dynamic reflection vulnerabilities, backends must never echo incoming origin headers automatically. Instead, they must enforce a strict, static Allow-List of trusted domains. If the incoming Origin is in the list, the server returns that origin; otherwise, it rejects the request entirely.

VII. Summary and Key Takeaways

The grammar of HTTP methods and the security borders of CORS constitute the legal framework of the web. By mapping intentions onto stable, uniform nouns and enforcing rigorous isolation boundaries, developers build systems that are resilient to network latency, transport failures, and malicious interventions.

Understanding these boundaries is not merely a tool for loading web pages; it is the fundamental framework of global distributed systems.
