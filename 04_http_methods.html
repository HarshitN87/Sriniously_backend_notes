Chapter the Fourth

HTTP Methods & The Same-Origin Borders

"GET, POST, and the delicate art of persuading the browser that your local server is not a compromised state actor trying to steal your bank cookies."
♦ ✦ ♦

Think of HTTP methods as the verbs of the web. Just as "sign" means different things depending on whether you are signing a guest book or a bank check, HTTP methods tell the server what action to perform on a resource. The URL is the noun (what resource), and the HTTP method is the verb (what action).

Two key ideas govern how these methods work: safety and idempotency. A safe method does not change the resource itself. A idempotent method produces the same result whether you call it once or many times.

Analogy: The Elevator Button vs. The Slot Machine. Pressing the elevator button for the 5th floor is idempotent: pressing it once or ten times gets you to the same place. Pulling a slot machine lever is not: each pull costs money and produces a different outcome. On the web, GET is like the elevator button, while POST is like the slot machine lever.

ASIDE

Idempotency means an operation gives the same result no matter how many times you repeat it. This is crucial for reliable networks, where requests may be retried due to timeouts or connection failures.

I. REST vs. RPC: Two Ways to Design APIs

When building APIs, you face a fundamental choice: should your URLs describe actions or resources?

RPC (Remote Procedure Call) treats the network like a set of remote functions. URLs look like actions: POST /api/createUser, POST /api/deleteUser. This is intuitive but becomes hard to manage at scale, because every team invents its own action names, and the network infrastructure cannot tell what each endpoint does.

REST (Representational State Transfer), formalized by Roy Fielding in 2000, flips this model. URLs identify resources (nouns), not actions. The HTTP method itself carries the action:

  • GET /api/users/42 — read the user
  • PUT /api/users/42 — replace the user entirely
  • PATCH /api/users/42 — update part of the user
  • DELETE /api/users/42 — remove the user

This separation lets proxies, CDNs, and browsers understand requests without knowing your application logic. GET responses can be cached; DELETE can be retried safely. REST is not always the right choice (gRPC and GraphQL are popular alternatives for internal microservices), but it provides a clean, predictable grammar for public APIs.

II. The Seven HTTP Verbs

HTTP defines a small vocabulary of methods, each with specific rules about safety, idempotency, and caching. Here is how they compare:

Method Safe? Idempotent? What It Does
GET Yes Yes Read a resource. The most common method. Responses are cacheable.
HEAD Yes Yes Same as GET but returns only headers, no body. Useful for checking metadata without downloading data.
POST No No Create a new resource or trigger a process. Each call may produce a different result. Not cacheable by default.
PUT No Yes Completely replace a resource. You must send the full resource. Repeating it leaves the resource in the same state.
PATCH No Usually No Apply partial changes to a resource. You send only the fields you want to change. More efficient than PUT for small updates.
DELETE No Yes Remove a resource. Deleting the same resource twice has the same effect: the resource is gone.
OPTIONS Yes Yes Discover what methods and headers a server supports. Used in CORS preflight checks.

GET & HEAD: The Passive Observers

GET is for reading only. It must not modify the resource itself (though the server may log the request or update analytics). Because GET is safe and idempotent, the entire web infrastructure optimizes for it: browsers cache it, proxies cache it, and CDNs replicate it globally.

HEAD is identical to GET but returns only headers. If you need to check whether a large file has changed, HEAD lets you inspect the ETag or Last-Modified headers without downloading the file. Search engines like Googlebot use HEAD extensively to avoid re-indexing unchanged pages.

POST: The Generator of State

POST is the most flexible and dangerous method. It creates resources, submits forms, or triggers processes. Because it is not idempotent, the server may create a new record every time you send it. Browsers warn you with "Confirm Form Resubmission" when you refresh a POST result, precisely to prevent accidental duplicates.

CAUTION

Because POST is non-idempotent, always protect it against duplicate submissions in payment or order systems. Use idempotency keys (unique tokens attached to each request) so the server can recognize and reject duplicates.

PUT vs. PATCH: The Complete Overwrite and the Surgical Strike

PUT replaces the entire resource. If a user has 20 fields and you only want to update the phone number, PUT still requires you to send all 20 fields. Any field you omit is treated as "delete this." PUT is idempotent because overwriting a record with the same data ten times leaves it in the same state.

PATCH updates only the fields you send. If you only want to change the phone number, you send just that field. This saves bandwidth but introduces a risk: if two clients PATCH the same resource at the same time, one update may overwrite the other (the "lost update" problem). To prevent this, servers use optimistic concurrency control: they send an ETag (version fingerprint) with the resource, and the client must include it in an If-Match header. If the resource changed since the client read it, the server rejects the update with 412 Precondition Failed, forcing the client to retry with fresh data.

III. Idempotency in Practice: Why It Matters

Networks are unreliable. A client may send a request, the server may process it, but the response may be lost. The client cannot tell whether the server received the request or not, so it retries. If the request was a POST (create a payment), the retry may create a duplicate charge.

The solution is the idempotency key. The client generates a unique token (like a UUID) and sends it with the request. The server stores this token and the response. If the same token arrives again, the server returns the stored response instead of re-executing the action. This turns a non-idempotent operation into a safe, repeatable one.

The key must be stored in the same database transaction as the business logic, so that if the transaction rolls back, the key is also rolled back. Otherwise, a failed transaction might leave the key set while the data is unchanged, causing the client to believe the operation succeeded when it did not.

IV. The Same-Origin Policy and CORS

The Same-Origin Policy (SOP) is a browser security rule that prevents a script on one website from reading data from another. An origin is defined by three things: the protocol (HTTP or HTTPS), the host (domain), and the port. If any of these differ, the origins are different, and the browser blocks the script from accessing the response.

Without SOP, a malicious site could load your bank page in the background and read your balance or transfer funds. SOP blocks this by default.

SECURITY

SOP and CORS are browser-only protections. They do not stop server-to-server requests or command-line tools. A backend server will still process a request from any source; the browser is what blocks the response from reaching the attacker's script.

Cross-Origin Resource Sharing (CORS)

Sometimes you need cross-origin access legitimately: your frontend lives on https://my-app.com and your API on https://api.my-app.com. CORS lets the server declare which origins are allowed to read its responses.

For "simple" requests (GET, POST with standard headers), the browser sends the request and checks the Access-Control-Allow-Origin header in the response. For "non-simple" requests (PUT, DELETE, PATCH, or requests with custom headers like Authorization), the browser first sends a preflight OPTIONS request to ask permission. Only if the server approves does the browser send the actual request.

CAUTION

Preflight checks add an extra round-trip. On slow mobile networks, this can hurt performance. Set Access-Control-Max-Age to cache preflight results and avoid repeating them.

Common CORS Security Mistakes

Dynamic Origin Reflection is a dangerous shortcut. Some developers echo the incoming Origin header back in the response, effectively allowing any website to access their API. This completely breaks SOP protection. Always use a strict allow-list of trusted domains instead.

Verb Tunneling is another risk. Some firewalls block PUT and DELETE, so developers tunnel them inside POST requests using an X-HTTP-Method-Override header. This bypasses firewall rules and can let attackers execute destructive actions through a seemingly harmless POST request.

SECURITY

CORS does not prevent CSRF (Cross-Site Request Forgery). A malicious site can still send a state-changing request to your server; CORS only blocks the response from being read. To stop CSRF, use anti-CSRF tokens or SameSite cookies.

V. Synthesis and Key Takeaways

HTTP methods are the grammar of the web. Choosing the right method makes your API predictable, cacheable, and safe to retry. Here is a quick reference:

Method Use For Can Retry? Cacheable?
GET Reading data Yes Yes
HEAD Checking metadata Yes Yes
POST Creating resources No (use idempotency keys) No
PUT Full replacements Yes No
PATCH Partial updates Usually no No
DELETE Removing resources Yes No
OPTIONS Capability discovery Yes Yes

Understanding these boundaries is the foundation of building reliable distributed systems. In the next chapter, we turn to the server's replies: the HTTP response codes that communicate success, failure, and everything in between.
