Chapter the Fourth

HTTP Methods & The CORS Protocol

"GET, POST, and the delicate art of persuading the browser that your local server is not a North Korean state actor trying to steal your bank cookies."
♦ ✦ ♦

Consider the physical act of holding a pen and dragging its graphite tip across a piece of paper to write your signature. On a purely mechanical level, the action is identical. It is the application of friction to wood pulp, guided by the neural circuits of your hand. But the semantic verb attached to this act determines the legal and material structure of the universe.

If you drag the pen across a guest book at a wedding, you are performing a passive, non-binding record of attendance. It has no side effects. It alters no rights. This is a GET. If you drag the pen across a bank check for ten thousand dollars, you are creating a brand-new financial instrument, generating a debit token that will cascade through the clearing houses. This is a POST. If you drag the pen across your previous last will and testament to replace it with a brand-new document containing entirely new beneficiaries, you are executing a complete, destructive overwrite of state. This is a PUT. If you drag the pen through a single clause of an existing contract to scratch out a spelling error while leaving the other thirty pages intact, you are performing a localized, partial mutation of state. This is a PATCH. If you drag the pen across a deed of release, declaring that a debt is cancelled and the record is formally expunged from the archives, you are executing a deletion. This is a DELETE.

The physical universe is indifferent to these differences. To the paper, it is all just ink and friction. But to the human coordination systems that stand behind the paper, the verb is everything. If you treat a bank check as a guest book—signing it twenty times because you like the feeling—you will bankrupt yourself. If you treat a will as a minor scratch-out, you will trigger decades of litigation.

Let us look at a second, more everyday analogy: the Elevator Button vs. the Slot Machine Lever. When you enter an elevator and press the button for the fifth floor, you are executing an idempotent operation. You press the "5" button once, and the elevator moves to the fifth floor. If you get impatient and hammer the "5" button ten more times, the elevator does not take you to the fiftieth floor. It does not double its speed. It does not charge you ten times. It simply registers that you wish to be on the fifth floor, a destination it has already committed to. Pressing the button one time or one hundred times produces the exact same final state.

Now, contrast this with the lever of a slot machine at a casino in Las Vegas. Each pull of the lever is a non-idempotent operation. Pull it once, and you spend one coin and roll the gears. Pull it three times, and you spend three coins and roll the gears three times. The state of your wallet, the state of the machine's memory, and the state of the casino's revenue matches the exact number of times you pulled the lever. If a network glitch pauses the universe and replay-attacks your lever pulls, you will be ruined.

These two concepts—Semantic Verbs and Idempotency—are the twin pillars of HTTP Methods. When we build backends, we are not merely receiving bytes; we are executing human intentions. If a client sends an HTTP request, the URL acts as the noun—identifying the target resource. But the HTTP method acts as the verb, declaring the semantic rules, the caching boundaries, and the mathematical safety profiles of the transaction.

1. The Grammar of REST vs the Imperative of RPC

To understand the semantic design of HTTP verbs, we must first contrast two competing philosophies of API design: RPC (Remote Procedure Call) and REST (Representational State Transfer).

In an RPC design, the URL represents an *action* or a *command*. The API paths look like verbs: POST /api/deleteUser or POST /api/updateAddress. In this imperative design, we rely almost exclusively on the POST method, using the URL to specify what action to run. It is simple, but as your system grows to thousands of endpoints, maintaining a unique verb path for every single operation becomes a chaotic naming puzzle.

REST (formalized by Roy Fielding in 2000)[1] flips this paradigm. In a RESTful API, the URL must strictly represent a noun—a unique physical resource. The URL path is clean and stable: /api/users/42 or /api/posts/928374. To dictate what action to perform on that noun, we do not edit the URL. Instead, we change the HTTP method verb at the protocol level.

If we want to read the user, we send GET /api/users/42. If we want to replace the user, we send PUT /api/users/42. If we want to delete them, we send DELETE /api/users/42. This decoupling creates a clean, elegant, self-describing API structure where the URL maps stable nouns, and the HTTP methods define the active verbs of your system.

Wait—let's argue with this model for a second. Is REST actually better?

In my early days of web development, I was a REST purist. I believed that anyone using RPC was an uneducated barbarian who had never read Fielding's dissertation. But then I tried to build a real system. How do you "deactivate" a user account in pure REST? Do you `PATCH` the user with `{"active": false}`? Or do you `POST` to `/api/users/42/deactivation`? If you choose the first option, you are treating deactivation as a simple database column write. But what if deactivation requires canceling Stripe subscriptions, sending emails, and logging the event in three security tables?

If you hide all those side effects behind a simple `PATCH` request, you are hiding a massive, state-mutating iceberg beneath a tiny column update. It violates the spirit of REST's predictability. Many modern API architectures, like gRPC or GraphQL, have quietly abandoned REST's taxonomic purity in favor of running everything over HTTP `POST` requests.[2] It turns out that when engineers are trying to build reliable systems, they prefer calling a command directly rather than debating whether deactivating a user is a `PUT` or a `PATCH`.

But REST remains highly effective for public-facing architectures because browsers and CDNs understand its verbs. If a request is a `GET`, they know they can cache the response forever without breaking anything. If it's a `POST`, they know they must never cache it. This global caching ecosystem is only possible because we agreed on a shared grammar.

2. Taxonomy of the Active Verbs

Let us dissect the primary verbs of the digital tongue:

  • GET: Requests a representation of the specified resource. GET is strictly a Safe Method—it is legally forbidden from mutating the server’s state. A GET request must only retrieve data; if a developer makes a GET request increment a counter in their database, they are violating the protocol contract.[3]
  • HEAD: Identical to a GET request, but with a critical optimization: the server must only return the headers, completely omitting the response body. Why is this useful? Imagine you want to download a massive 5GB zip file. Before wasting your bandwidth, you send a HEAD request. You inspect the Content-Length header to check the size, or the Last-Modified header to verify if your local cached copy is out of date. It is an efficient way to inspect a resource without downloading the cargo.
  • POST: Submits an entity to the specified resource, often causing a change in state or side effects on the server (like creating a new record in a database or charging a credit card). POST is neither safe nor idempotent.
  • PUT: Replaces all current representations of the target resource with the request payload. PUT is a total replacement. If a user resource has ten columns, and you send a PUT request containing only a new name, the other nine columns must be set to null or default values. PUT is mathematically idempotent.
  • PATCH: Applies partial modifications to a resource. Unlike PUT, PATCH is a differential update. If you send a PATCH request containing only a new name, the server updates only the name column, leaving the other nine columns completely untouched. PATCH can be implemented in a non-idempotent manner.
  • DELETE: Deletes the specified resource. It is mathematically idempotent.
  • OPTIONS: Retrieves the communication options supported by the target server. It acts as the diplomatic scout, which we will inspect during our CORS audit.

Let us look at the deep engineering differences between PUT and PATCH. Novice developers often use them interchangeably, but their logical differences inside the database layer are immense. When you run a PUT query, the server expects a complete resource object. It compiles an insert-or-replace statement: UPDATE users SET name = $1, age = $2, email = $3 WHERE id = $4;.

If the client omitted the email variable in the PUT payload, the server binds null to $3, wiping out the user's email address from the database!

To run a PATCH query, the server must construct a dynamic update query at runtime, updating only the columns that were explicitly sent: 

// Dynamic compilation in Node.js
const fields = Object.keys(req.body).map((key, i) => `${key} = $${i + 1}`).join(', ');
const query = `UPDATE users SET ${fields} WHERE id = $${fields.length + 1}`;

This dynamic query compilation requires additional processing overhead on the server, but it protects your database columns against accidental wipes, making PATCH the ideal choice for partial forms and settings pages.

3. The Laws of Idempotency: The Elevator and the Vending Machine

Let us formalize the law of Idempotency. In mathematics, an operation is idempotent if applying it multiple times yields the exact same outcome as applying it once: $$f(f(x)) = f(x)$$

In HTTP, a method is idempotent if making multiple identical requests results in the exact same server state as making a single request.

Let us look at a common point of confusion: why is DELETE idempotent? If you send DELETE /api/posts/42, the server deletes post 42 and returns a `200 OK` status. If you send the exact same delete request a second time, post 42 is already gone. The server looks at the database, finds nothing, and returns a `404 Not Found` response.

The *response code* is different (200 vs 404), but the state of the server's database is identical. In both cases, post 42 does not exist. Because the final state of the database remains unchanged between request #1 and request #100, DELETE is completely idempotent.

But wait—what's the actual mechanism here when handling non-idempotent operations in real-world high-reliability networks?

Imagine a customer clicking "Buy Now" on a Stripe checkout page. The browser fires a non-idempotent `POST` request to charge their credit card. The server receives the request, charges the card, and fires back a success packet. But in mid-ocean, a fiber repeater drops the returning success packet.

To the browser, the request timed out. The user, seeing no confirmation, clicks the "Buy Now" button again. Without guards, the server would charge their card a second time. To prevent this, Stripe utilizes Idempotency Keys. Before firing the request, the client generates a unique UUID (e.g., Idempotency-Key: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d) and attaches it to the HTTP headers.

When the server receives the request, it checks a fast Redis cache. If the key does not exist, the server executes the transaction and stores the result against that key. If a second request arrives with the *exact same idempotency key*, the server does not run the billing code again. It simply reads the cached result from Redis and hands it back, ensuring the customer is only billed once, even if they hit submit fifty times.

4. Same-Origin Policy (SOP) and CORS: The Cautious Diplomats

Let us shift our focus to the browser's security boundaries. The browser is a shared arena where you run multiple tabs simultaneously: your bank portal in one tab, and a sketchy movie site in another. In 1995, engineers at Netscape realized that this shared arena was highly dangerous. If the movie site could run a script that queried your bank portal in the background, it could read your bank's cookies, steal your private balances, or transfer funds.[4]

To prevent this, Netscape Navigator 2.0 introduced the Same-Origin Policy (SOP). SOP dictates that a script running on one origin is strictly forbidden from reading or writing resources loaded from a different origin. An Origin is defined as a strict 3-tuple: $$\text{Origin} = (\text{Protocol}, \text{Host}, \text{Port})$$

If any of these three variables differ, the resources are cross-origin:

  • https://my-bank.com and http://my-bank.com are cross-origin (different Protocol).
  • https://my-bank.com and https://api.my-bank.com are cross-origin (different Host).
  • https://my-bank.com:443 and https://my-bank.com:8080 are cross-origin (different Port).

While SOP protected users, it created massive headaches for early developers. If your frontend was hosted on https://my-app.com and your API lived on https://api.my-app.com, the browser blocked your frontend from making AJAX calls to your own backend!

To bypass this boundary, developers used a clever smuggling route called JSONP (JSON with Padding). While SOP blocked AJAX requests, it made an explicit exception for the <script> tag, because sites needed to load libraries from external CDNs.

A developer would inject a script tag dynamically into their page: <script src="https://api.my-app.com/users?callback=handleUserData"></script>. The backend, seeing the callback query, would return the JSON data wrapped inside a JavaScript function call: handleUserData({"username": "harshit"});.

When the browser finished downloading the script, it executed the callback function, allowing the frontend to read the data. While JSONP worked, it was extremely insecure. It was strictly limited to GET requests, and it meant allowing third-party servers to execute arbitrary JavaScript code inside your page, exposing you to massive Cross-Site Scripting (XSS) risks.

To replace this smuggling, the W3C formalized CORS (Cross-Origin Resource Sharing). CORS is a protocol that allows servers to explicitly declare who is allowed to visit them. Under CORS, requests are divided into two categories:

  1. Simple Requests: Safe methods (like GET or POST with standard form types) that do not carry custom headers. The browser sends the request directly, adding an Origin header. The server replies. The browser inspects the response headers: if it does not find Access-Control-Allow-Origin: * or a matching origin, the browser blocks the JavaScript code from reading the response.
  2. Preflighted Requests: Any request that uses non-standard methods (like PUT, DELETE, PATCH) or custom headers (like Authorization). The browser is terrified that these requests might perform destructive mutations on the server. Before sending the actual request, the browser dispatches an OPTIONS Preflight Request.
Plate X: The CORS Preflight OPTIONS Handshake

The preflight scout carries three administrative query headers:

  • Origin: https://my-app.com
  • Access-Control-Request-Method: PUT
  • Access-Control-Request-Headers: Authorization

The server receives this OPTIONS scout, evaluates whether https://my-app.com is a trusted origin, and replies with standard CORS allow headers:

  • Access-Control-Allow-Origin: https://my-app.com
  • Access-Control-Allow-Methods: GET, POST, PUT, DELETE
  • Access-Control-Allow-Headers: Authorization
  • Access-Control-Max-Age: 86400 (caches the preflight decision for 24 hours)

Only after this preflight check succeeds does the browser launch the actual PUT request containing your data payload.

Let us clarify a fundamental security concept: CORS is strictly a browser-enforced boundary. CORS is *not* a firewall on the server that blocks incoming requests. If you make a request to a server using a terminal tool like `curl` or a backend python script, the server does not perform any CORS checks. The server processes the query and returns the bytes normally.[5]

CORS only exists inside the browser sandbox, where the browser checks the headers *after* receiving the reply to decide whether to expose the data to your JavaScript. Therefore, CORS does not protect your server's endpoints from being scraped or hammered by bots; it only protects your users from having their browser sessions hijacked by malicious sites.

5. Key Takeaways
